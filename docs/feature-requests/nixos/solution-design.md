# Solution Design: NixOS Declarative Development Environment

## Approach

Ansible is a **thin deploy driver** (Option A). No apt-based role is applied to
the NixOS guest; all guest configuration lives in a committed Nix flake built by
`nixos-rebuild`. The bootstrap reuses only the clone / boot / reach-SSH prefix
of `playbooks/tasks/create/tart.yml`, then runs `nixos-anywhere` to convert the
booted Ubuntu VM in place to NixOS. This keeps the Ansible surface small and
adds no separately maintained image artifact.

The flake is structured with a shared configuration module plus a thin
per-provider hardware/bootstrap module. **v1 creates only the shared module and
the Tart hardware module** — the deferred provider modules are not created until
their own increments (Constitution Principle XIII, no empty artefacts;
Principle IV, no speculative generalisation). The split itself is near-zero cost
and mirrors NixOS's own configuration-vs-hardware idiom, so it is DRY-ready
without pre-building for absent targets.

## OS-axis dispatch decision

The existing dispatch has two axes only — **provider**
(`create-vm.yml` dispatches on `{{ provider }}`) and **profile** — and
`tasks/assert-provider-profile.yml` hard-codes the provider set
(`tart`, `docker`, `hcloud`, `aws`). NixOS on Tart is neither a new provider nor
a profile; it is a **different guest OS on the same provider**. The design must
choose one concrete mechanism, and the choice threads through `create-vm.yml`,
`assert-provider-profile.yml`, `destroy-vm.yml`, and the inventory group writes
(currently `linux` + `tart`). Candidates:

- a new provider string (e.g. `tart-nixos`);
- a new orthogonal `os=nixos` axis;
- a flag on the existing `create/tart.yml` path.

This is an ADR-worthy decision in its own right and is captured in the ADR named
under "Constitution mapping" below. It must be resolved as part of Increment 1
(the spike may prototype it informally).

## Post-conversion identity, inventory, and host key

`nixos-anywhere` repartitions the disk, so everything `create/tart.yml`
establishes after boot is destroyed: the `admin` user
(`admin_user_on_fresh_system`), its injected `authorized_keys`, and the Ubuntu
SSH host key. The convert step must therefore:

1. **Bake `my_ssh_public_key` into the flake** for the `galadriel` user — the
   same variable ADR-004 already threads through, referenced once (DRY), not
   copied. `nixos-anywhere` places it via `--extra-files` / the flake so the key
   exists in the fresh closure before first boot.
2. **Provide an auth path for `nixos-anywhere` into the kexec'd installer** —
   the operator key reachable over the booted Ubuntu SSH session before the
   wipe.
3. **Rewrite the autogenerated inventory** entry from `ansible_user: admin` to
   `ansible_user: galadriel`, so subsequent `nixos-rebuild` / `destroy` runs
   connect correctly.
4. **Handle the changed host key.** For Tart (local, NAT-bridged) Principle XIV
   permits `StrictHostKeyChecking=no`, which `create/tart.yml` already uses — so
   v1 is compliant. For the deferred cloud path, Principle XIV requires
   `accept-new` + a gitignored `known_hosts` and a *stable* key across
   conversion; pre-seed the NixOS host key declaratively (via
   `nixos-anywhere --extra-files` / disko) so it does not rotate mid-flight.
   Cloud XIV compliance is a follow-on obligation on the provider increments,
   flagged here so "reuse the shared module" is not read as zero-cost.

## Control-node prerequisites (hard preconditions)

`nixos-anywhere` is itself a Nix flake app; it requires Nix with flakes on the
machine that runs it — the macOS Tart host. These are preconditions for
Increment 0 to start, not open questions, and each gets a fail-loud preflight
(Principle XII), mirroring the existing `sshpass` check in `create/tart.yml`:

- **Nix with flakes enabled** on the control Mac.
- **An aarch64-linux build path.** macOS cannot natively build Linux
  derivations; the aarch64-linux closure must be produced via
  `nixos-anywhere --build-on-remote` (the guest builds itself) or a configured
  Linux builder. Resolve this before day one, or the spike stalls on a builder
  error unrelated to kexec.
- **Constitution stack note.** Nix on the control node is a new tool on the
  control plane; the constitution's Technology Stack gates additions, so the ADR
  records the one-line justification (control-node-only, required by
  `nixos-anywhere`).

## Bootstrap mechanism by provider

| Provider | Mechanism | Bootstrap risk |
| --- | --- | --- |
| Tart (v1) | `nixos-anywhere` (kexec + disko) on a booted Ubuntu VM | Unknown — aarch64 under Apple Virtualization.Framework; retired by Increment 0 spike |
| Hetzner Cloud | `nixos-anywhere` from a base image or rescue system | Near-zero — canonical `nixos-anywhere` target |
| AWS EC2 | `nixos-anywhere`, or launch an official NixOS AMI directly | Low — two independent paths |
| NixOS-WSL (Windows) | Tarball import via `wsl --import` | Low — distinct mechanism, no kexec/disk |
| Docker | Not applicable — no disk, bootloader, or kexec | Excluded permanently |

Only the per-provider hardware/bootstrap module varies across rows; the shared
configuration module is identical.

### Fallback: maintained snapshot base image

If the spike shows `nixos-anywhere` is unviable on Tart, the fallback is a
one-time manual NixOS install (from the ARM64 ISO) snapshotted into a reusable
Tart base image, cloned cheaply thereafter. Trade-off versus convert-in-place:
it removes the kexec/disko risk entirely and makes create fast and
deterministic, at the cost of an image artifact to maintain and refresh, and a
manual bootstrap step that is not itself reproducible from the flake. Named here
so the pivot is a comparison, not an improvisation.

## Flake structure (sketch — v1 creates only shared/ and providers/tart.nix)

```text
flake.nix
  nixosConfigurations.<host> = shared-config + tart-hardware
modules/
  shared/                 # dev-environment definition (packages, users, sshd)
  providers/tart.nix      # Tart hardware + disko layout (see hypotheses below)
```

The deferred `providers/hetzner.nix`, `providers/aws.nix`, and
`providers/wsl.nix` are **not created in v1**; each is added in its own
increment with real content. The word "provider" on the Nix side denotes a
hardware profile, distinct from the Ansible infra providers.

The concrete host name is drawn from the Tart hostname pool
(`playbooks/vars/hostname_pool_tart.yml`), not hard-coded here.

### Hardware hypotheses to confirm in the spike (not yet decided)

The following are the Increment 0 spike's job to confirm empirically, not
committed facts: the disk device name (likely `/dev/vda` under virtio),
firmware (UEFI vs BIOS under Apple Virtualization.Framework), the disko layout
(ext4 vs btrfs, subvolumes), and whether an aarch64 kexec installer image boots
under this hypervisor at all.

## Constitution mapping (record as an ADR + a plan.md Complexity Tracking entry)

The declarative guest relocates the constitution's rules; the ADR documents the
decisions so compliance is explicit. Governance also requires the exception to
appear in the eventual `plan.md` Complexity Tracking table referencing the ADR —
the ADR alone is not sufficient.

- **Idempotency (Principle I)** is split into two distinct steps:
  - the `nixos-anywhere` **convert** step is destructive and one-shot, so it is
    **guarded** — it detects an already-converted host and does not re-image
    unless an explicit re-image flag is passed;
  - `nixos-rebuild switch` against the flake is idempotent by construction and
    **always runs** on re-apply (it converges to the flake; it is not a no-op
    when the flake changed). The whole-playbook re-run is therefore not a
    no-op — only the convert step is.
  - **Guard detection predicate**: the guard probes the target and treats it as
    already-converted when NixOS is detected (e.g. `/etc/os-release` reports
    NixOS, or an SSH login as `galadriel` succeeds where the fresh-Ubuntu
    `admin` path would be expected). The exact predicate is fixed in
    Increment 1 and validated by Fail-Loud preconditions (Principle XII).
- **Role-first / Molecule (Principle II)**: **no new Ansible role is
  introduced.** The convert step is create-path task-file orchestration, exactly
  like the existing `tasks/create/{provider}.yml` files, which have never been
  roles and are not on the closed maintenance-playbook allowlist — the ADR
  states that create-path task files are treated as orchestration, consistent
  with existing practice. Because there is no role, Molecule (which is scoped to
  containerizable roles) does not apply; this is a cleaner argument than "the
  role cannot be containerized."
- **Test strategy** (the NixOS-native replacement for Molecule):
  `nix flake check` (validity) + `nixos-rebuild build` /
  `nix build .#nixosConfigurations.<host>.config.system.build.toplevel`
  (evaluates and builds the full closure without touching a host) + a
  `nixosTest` boot test (the "does it come up" analog) once CI exists.
- **Spike exemption**: the Increment 0 spike is exempt from the full test gate
  while it is a spike (its deliverable is knowledge). The exemption ends the
  moment its code is promoted into Increment 1.

## Work breakdown

Ordered increments, each with a one-line acceptance criterion. Increment 0 is a
time-boxed spike whose code is promoted into Increment 1 on success rather than
thrown away.

0. **De-risk spike (review checkpoint, target ≤ 3 days).** Graded outcomes, not
   binary: (a) full success — a converted Tart VM boots into NixOS and SSH login
   as `galadriel` succeeds → promote the spike code; (b) kexec + disko succeed
   but boot/network fails (e.g. bootloader won't install on this UEFI, or the
   guest never returns on its DHCP lease) → time-box one further day on the
   specific sub-failure, else pivot; (c) kexec unsupported at all → immediate
   pivot to the snapshot-base-image fallback. The ≤ 3 days is a review point,
   not a success deadline. Set VM memory high enough for the in-RAM kexec
   installer to avoid OOM.

1. **Bare-boot MVP.** Provisioning a fresh Tart VM yields an SSH-reachable NixOS
   host (as `galadriel`) whose entire configuration comes from the committed
   flake; the convert step is guarded (re-run does not re-image, verified
   minimally); the autogenerated inventory records `ansible_user: galadriel` and
   `destroy` works; `destroy → re-create` reproduces the same system closure;
   `nix flake check` passes; the ADR and Complexity Tracking entry are written;
   the OS-axis dispatch mechanism is chosen and wired.

2. **Minimal base tooling.** After provisioning, `git`, `vim`, `tmux`, the login
   shell, `ruby`, `python`, `nodejs`, and `podman` all report versions, are all
   declared in the flake, and `nix flake check` passes.

3. **Daily-driver ergonomics (home-manager).** A freshly provisioned VM comes up
   with the shell prompt/aliases, tmux config, git identity, and SSH setup
   already in place, requiring zero manual post-setup. Requires the
   Vault-vs-Nix secret decision (see PRD) to be resolved first if any secret is
   involved.

4. **Custom tooling, one tool per sub-increment (easiest packaging first).** For
   each of `rtk`, `beads`, `specify_cli`, `opencode`, `claude_code`, the tool
   runs a smoke command on a freshly provisioned VM and is pinned reproducibly
   in the flake (flake input, overlay, or `fetchurl`). Ordering establishes the
   packaging pattern on a cheap tool before the awkward ones.

5. **CI gate and hardening.** CI runs `nix flake check` plus a `nixosTest` boot
   test on every change; the destructive-step guard gains its automated
   regression test; docs/ADR describe the reprovision and pivot story.

## Deferred provider increments

Added after the local loop is proven, reusing the shared configuration module
and each creating its provider module at that point (never before):

- **Hetzner Cloud** — `nixos-anywhere` from a base image or rescue system.
- **AWS EC2** — `nixos-anywhere` or an official NixOS AMI.
- **NixOS-WSL (Windows laptop)** — a new `wsl` create step (`wsl --import` of a
  NixOS-WSL tarball) plus a `providers/wsl.nix` module; the shared configuration
  module is reused verbatim. Intended replacement for the owner's current
  Docker-based local runtime on Windows.

## Open questions

1. Does an aarch64 `nixos-anywhere` kexec image boot on Tart under Apple
   Virtualization.Framework? (Resolved empirically by Increment 0 — the spike's
   whole point.)
2. Does the converted Tart VM retain its DHCP IP through the kexec and the final
   reboot, or must the inventory IP be re-resolved via `tart ip`? (Verify in the
   spike; likely place for a silent hang.)
3. Which disko layout (ext4 vs btrfs, subvolumes) is preferred? (Decided during
   Increment 1; not blocking the spike.)
