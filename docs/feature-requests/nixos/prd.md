# PRD: NixOS Declarative Development Environment

## Problem

Every managed Linux host in this repository runs Ubuntu, configured
imperatively by apt-based Ansible roles. There is no reproducible,
declaratively-defined development-environment runtime: the state of a dev VM
is the sum of many imperative role executions, which is hard to reason about,
reproduce byte-for-byte, or roll back.

The owner wants a development environment whose entire definition — packages,
services, users, system configuration — lives in a single committed source of
truth that reproduces the same system on demand. NixOS provides exactly this
model: the whole machine is described in one declarative configuration and
built atomically by `nixos-rebuild`.

## Goal

Provision a NixOS-based development VM in which:

- Ansible acts as a **thin deploy driver only** — it creates the VM and runs
  the NixOS build. It does not configure the guest with imperative roles.
- A committed **Nix flake is the single source of truth** for all packages,
  services, and system configuration on the guest.
- The flow is proven **locally first** (Constitution Principle III) before any
  cloud target is attempted.

This is an epic. The first increment is a **de-risking milestone**, not yet a
usable development environment: a reproducible, bootable, SSH-reachable NixOS
host on the local Tart provider — nothing more. It is valuable as a
*reproducibility capability* (destroy and re-create yields the same system from
a committed flake), which is the thesis the whole epic rests on; it is
explicitly not a daily-driver dev box yet. Dev tooling, ergonomics, cloud, and
Windows are deferred to later increments so the highest-risk unknown is retired
before any high-effort work begins. The ordered breakdown lives in
`solution-design.md`.

## Scope (v1 — the MVP)

- **Provider**: Tart (local, Apple Silicon ARM64) only.
- **Shape**: headless CLI host (no desktop GUI).
- **Bootstrap**: `nixos-anywhere` converting a booted Ubuntu Tart VM in place
  to NixOS. This reuses **only the clone / boot / reach-SSH prefix** of the
  existing `playbooks/tasks/create/tart.yml`; the post-conversion identity and
  inventory handling is new work (see below and `solution-design.md`). No
  prebuilt NixOS image is built or maintained.
- **Configuration**: a committed flake providing `sshd` and the `galadriel`
  user, whose `authorized_keys` is populated from the **existing
  `my_ssh_public_key`** variable (the same key ADR-004 threads through — one
  source, not a second copy), plus the minimum needed to boot and log in.
- **Identity/inventory contract**: `nixos-anywhere` wipes the disk, so the
  `admin` user, its injected key, and the Ubuntu host key created by
  `create/tart.yml` do not survive. The convert step must therefore (a) ensure
  the flake bakes `my_ssh_public_key` for `galadriel`, and (b) rewrite the
  autogenerated inventory entry from `ansible_user: admin` to
  `ansible_user: galadriel`. `destroy` must still work against a converted
  host.
- **De-risk first**: an Increment 0 spike (time-boxed **review checkpoint**,
  not a binary deadline) proves that `nixos-anywhere` (kexec + disko
  repartition) works on Tart aarch64 under Apple Virtualization.Framework
  **before** any tool or config scope is committed. Graded outcomes and the
  pivot rule are defined in `solution-design.md`.

## Out of scope (v1)

Deferred to later increments (see `solution-design.md` for the ordered
breakdown), not permanently excluded:

- Cloud providers (Hetzner Cloud, AWS EC2).
- A Windows runtime (NixOS-WSL is the intended mechanism — see below).
- Desktop / GUI environment.
- Packaging the repository's custom tooling for Nix (`claude_code`,
  `opencode`, `rtk`, `beads`, `specify_cli`).
- Core nixpkgs dev tooling beyond what is needed to boot and log in.
- CI gating for the Nix configuration.
- **Secrets in the flake.** v1 commits only a *public* key, so no secret is
  stored. Any later increment that needs a secret (git identity beyond public
  config, tokens) MUST first resolve how Ansible Vault (Secret Management,
  constitution) reconciles with a NixOS secret mechanism (sops-nix / agenix).
  That reconciliation is a required decision **before Increment 3** and is a
  candidate ADR; it is not attempted in v1.

Permanently excluded:

- **Docker as a NixOS target.** A container is not a machine — no disk to
  partition, no bootloader, no `kexec` — so `nixos-anywhere` cannot target it,
  and a full declarative NixOS *system* cannot run there. Docker remains a
  role-test sandbox for the existing Ubuntu roles only.

## Deferred future targets

- **Hetzner Cloud** — `nixos-anywhere`'s canonical target; near-zero
  bootstrap risk (KVM, working kexec, native rescue system).
- **AWS EC2** — `nixos-anywhere` works on Nitro/KVM instances; additionally
  official NixOS AMIs exist as an independent fallback path.
- **Windows laptop** — via **NixOS-WSL**: a real NixOS distribution under
  WSL2, configured by the same shared flake. Bootstrap differs (tarball import
  via `wsl --import`, not `nixos-anywhere`), so it is a distinct create step
  reusing the shared configuration. Intended replacement for the owner's
  current Docker-based local runtime on Windows.

## Key decisions and rationale

Rationale is kept brief here; the mechanics live in `solution-design.md`.

1. **Ansible = thin driver (Option A), not apt-role reuse.** On NixOS the
   imperative convergence Ansible roles perform is the OS's own native job.
   Forcing the apt roles onto NixOS fights the design (read-only `/nix/store`,
   no FHS `/usr/bin`, system-managed `/etc`).
2. **Bootstrap via `nixos-anywhere` on a booted Ubuntu VM.** No turnkey NixOS
   Tart image exists; the only documented Tart path is a manual ISO install,
   unsuitable for repeatable automation. Converting the image the repository
   already boots avoids both a manual step and a separately maintained image
   artifact. Fallback if the spike fails: a maintained snapshot base image or
   direct ISO install (trade-offs in `solution-design.md`).
3. **Spike-first bare-boot MVP.** All candidate scopes share the same risky
   prefix (does `nixos-anywhere` work on this hypervisor?). Custom-tool
   packaging is the highest-effort, most-certain work; placing it behind the
   highest-uncertainty gate would be a gamble. Isolate and prove the unknown
   with the least else attached.
4. **Provider-agnostic *split*, not provider-agnostic *stubs*.** The flake is
   split into a shared configuration module plus a per-provider hardware module
   so a future second provider reuses the shared module (Constitution
   Principle XI, DRY). v1 creates **only** `shared/` + `providers/tart.nix`;
   the deferred provider files are NOT created until their increment (avoids
   Principle XIII empty artefacts and Principle IV speculative generalisation).

## Constitution interaction

The declarative guest relocates — does not remove — the constitution's rules.
The detailed mapping and the required governance artefacts (an ADR **and** a
`plan.md` Complexity Tracking entry that references it) are in
`solution-design.md`. In brief: idempotency is delegated to `nixos-rebuild`;
no new Ansible role is introduced (the convert step is create-path
orchestration, so Molecule does not apply); YAGNI and test-local-before-cloud
are honored by the Tart-only, spike-first, bare-boot scope.

## Acceptance criteria (MVP)

1. Running the provisioning playbook against a fresh Tart VM produces an
   SSH-reachable NixOS host reachable as `galadriel`, whose **entire**
   configuration comes from the committed flake.
2. The autogenerated inventory entry for the host records
   `ansible_user: galadriel` (not `admin`) after conversion, and `destroy`
   succeeds against the converted host.
3. The destructive `nixos-anywhere` convert step is **guarded**: re-running the
   playbook against an already-converted host detects that state (predicate
   defined in `solution-design.md`) and does not re-image. A re-run that
   re-applies the flake via `nixos-rebuild switch` converges idempotently — it
   is not required to be a whole-playbook no-op, only the convert step is.
4. Minimal verification of the guard is demonstrated in this increment (a
   re-run does not re-image); the *automated regression test* for the guard is
   deferred to the CI increment.
5. `destroy` followed by re-create reproduces the same system closure.
6. `nix flake check` passes for the committed configuration (requires the
   control-node Nix prerequisite — see `solution-design.md`).
7. An ADR records the Molecule-exemption argument, the test strategy, the
   destructive-step-guard decision, and the OS-axis dispatch decision; a
   `plan.md` Complexity Tracking entry references it.
8. The Increment 0 spike outcome is documented — the technique is proven and
   its code promoted into the MVP, or a graded pivot is recorded.

## Risks

- **Primary**: `kexec`/disko repartition under Apple Virtualization.Framework
  on aarch64 may be unsupported or rough. Retired by the Increment 0 spike;
  bounded by the review checkpoint; cloud providers remain a fallback if Tart
  cannot host the local loop.
- **Control node**: `nixos-anywhere` and `nix flake check` require Nix (with
  flakes) on the macOS host that runs Tart, and building an aarch64-linux
  closure from macOS needs `--build-on-remote` or a Linux builder. This is a
  hard precondition, not an open question (see `solution-design.md`).
- **Bricked convert**: a mid-repartition failure destroys the Ubuntu image;
  recovery is destroy + re-clone (no in-place rollback). Acceptable but
  explicit.
- **Secondary**: custom-tool Nix packaging effort (deferred); handled one tool
  per increment, easiest packaging first.
